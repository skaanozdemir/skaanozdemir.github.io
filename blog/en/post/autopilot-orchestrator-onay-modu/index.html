Autopilot in production Orchestrator: seven steps for the approval mode

Autopilot Chat returned to Orchestrator on 28 October and can now manage queues, assets and triggers. A decision table for which approval mode belongs in which tenant, and seven checks before production.

Playbook·RPA & orchestration·November 5, 2026·6 min read·Türkçesini okuyun

The Autopilot Chat that came back to Orchestrator can manage processes, jobs, queues, assets, triggers, machines and folders in your tenant. That makes it an operator, and the decision that matters when you turn it on is which approval mode runs in which tenant. The documentation leaves two of the questions behind that decision open: what permissions Autopilot acts with, and what trail it leaves. The steps below are for closing those gaps before production.

At BOTTEQ we work with clients on Orchestrator topology, tenant and environment design, asset and credential management and queue architecture. The product facts in this guide come from UiPath’s own pages, listed at the end. The recommendations and the decision table are my opinion.

What changed

UiPath removed Autopilot Chat from Orchestrator on 14 October, saying it would return with improved features. According to the 28 October release notes, it is back. The capability list in the user guide is broad: operating processes, jobs, queues, assets, triggers, machines, folders and storage buckets; investigating failed jobs and access issues; inspecting audit events; and planning, building and deploying automations. Projects themselves are created in Studio Web.

You pick the approval mode from a dropdown under the chat box, and there are three:

  • Cautious asks before every operation. UiPath calls it the safest option.
  • Adaptive auto-approves known safe operations and is the one UiPath recommends. Turn on Smart approvals and it also approves operations the model judges safe. The page states plainly that the model can misjudge.
  • Full access shows no approval prompts. The page says to use it only in trusted environments.

Settings has five tabs: tools (such as web search and the web reader), built-in skills, MCP servers, personalisation (including a custom instruction added to every prompt), and a security tab that lists the sites Autopilot may use without asking and the ones it won’t open. The AI capabilities need an active AI Trust Layer policy deployed to the tenant. The feature availability table shows Autopilot Chat in Automation Cloud and Test Cloud, but not in the Public Sector or Dedicated offerings.

Three things I could not find on the page: whether Autopilot acts with the signed-in user’s roles, who can connect an MCP server and whether that is scoped to a user or the tenant, and whether Autopilot’s own changes are logged separately. Their absence doesn’t mean anything is wrong. It means they aren’t written down, and a production decision needs them written down.

A decision table for the approval mode

The cost in the production row is real. A tool that asks before every operation can turn into a “yes” button within a week. My way round it is to use Autopilot in production for reading and investigation first, and to push any change through the change process you already have.

Seven steps before production

  1. Write down the tenant list. Put on one page which tenants will have Autopilot switched on. Tie the AI Trust Layer policy deployment to that list so the decision lives in one place.
  2. Test the permission model yourself. In the test tenant, sign in as a user with limited rights. Ask Autopilot to change an asset in a folder that user cannot edit. Record what happens and the error text. The documentation doesn’t say, so this is the only way to know it stays inside the user’s roles.
  3. Fix the approval mode per tenant. Announce the split in the table to the team. If users pick the mode themselves, “no Full access in production” has to be a written rule. Try in the test tenant whether you can also enforce it technically.
  4. Keep Smart approvals off in production. It hands the approval decision back to the model. UiPath’s own warning is reason enough. Turn it on in the test tenant for a week and note which operations it approved on its own; make the production call from that list.
  5. Start with no MCP servers. Every MCP server you connect gives Autopilot new tools, which means a new area of authority. Connect none on day one in production. For each one you add later, record its owner, the tools it exposes and the identity it runs under. Since it isn’t documented who can connect one, check the list regularly in the first week.
  6. Open web access on purpose. Web search and the web reader are tools, and the security tab holds the sites Autopilot may use without asking. Keep that list short in production. Tenant data and text from outside sources meeting in the same session is a risk worth thinking through on its own.
  7. Build the trail independently of Autopilot. The page says chat history shows the last thirty days and can be downloaded as JSON. That isn’t a change record. In the test tenant, have Autopilot change an asset, then look in the Orchestrator audit log to see whose name the change appears under. The same release brought another change: you can now record failed jobs and failed queue transactions together for one process. Previously you had to choose one, so a job that failed during initialisation left no recording if you had chosen queue transactions. Turn it on for critical processes, so that when you ask Autopilot or a person why a job failed, there is evidence to look at.

Most of these steps aren’t new. We already write code review standards, release management, bot monitoring, incident response and hypercare rules into client organisations. Autopilot adds one more actor to those rules: a model making changes from a user’s session.

When not to use this guide

  • It isn’t in your cloud offering. On Public Sector or Dedicated, the table doesn’t apply yet. If you run in your own data centre, check your version’s documentation separately.
  • You have no test tenant. Three of the seven steps need one. For a small team on a single tenant, using Autopilot only to ask questions is the better choice.
  • Production changes go through a change board. Then even Cautious isn’t enough: whatever Autopilot proposes has to go to the board. Its value stays on the investigation and diagnosis side, which is not a small value.

The question for Monday

Ask your team one thing: “If Autopilot switched off a trigger in production, which record would show it tomorrow morning, and under whose name?” If you can show the answer in the test tenant, switch it on. If you can’t, do step seven first.
