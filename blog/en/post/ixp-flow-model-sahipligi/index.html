IXP models now live inside Maestro Flow, so the flow owner owns the document model

Since 30 October the Extract node in Maestro Flow builds an IXP model on the canvas and ships it with the solution. Ownership moves to the flow team. Five gaps the documentation leaves open, and how I would close them before production.

Analysis·Document AI·November 19, 2026·6 min read·Türkçesini okuyun

Since 30 October, the Extract node in Maestro Flow can build an IXP extraction model directly on the canvas, and that model is deployed together with the solution the flow belongs to. On paper it’s a convenience: no separate application for the document model. My reading is that the real change is ownership. The person who builds, tests and versions the model is now the person who builds the flow. I think that’s the right direction. UiPath’s own documentation, though, leaves five gaps that matter in production, and they’re worth closing before anything goes live.

What changed

According to the October release notes, the Extract document option on the Extract node creates a new IXP model. Taxonomy, model configuration and validated predictions are all set up on the canvas, and the feature is in preview. The model counts as a solution resource: when the solution is deployed, the model is packaged with it, and the documentation says no extra manual step is needed in the target environment. Solution packages are versioned, so you can upgrade or roll back.

The reuse rules are clear. Another flow in the same solution picks the model up through In this solution. A flow in a different solution only sees it through Published, after the owning solution has been deployed. If you bind a model published from the IXP application, its taxonomy and configuration become read-only in the node. The model can also be called from outside Flow, through the Document Understanding activities in Studio or version 2 of the Document Understanding API.

The same release added a Validate extraction node in the Human category. It sends the Extract node’s output to a person, who checks and corrects the data before the run continues. A fix on 17 November turned a type mismatch on that node’s document input from an error into a warning, so it no longer blocks debugging or publishing.

Why ownership moves

In document processing, the model itself is rarely what takes the most time. The flow around it does: exception rules, the validation screen, getting corrected data back into the system. In the on-premise document-processing programme we built for a national flag carrier, validation station design and structured human-in-the-loop escalation sat at the centre of the work. At BOTTEQ we build these lines by combining UiPath Document Understanding with Base64.ai’s OCR/ICR engines. Where model and flow are run by separate teams on separate calendars, a common failure is a taxonomy change made without anyone telling the validation rules in the flow.

Shipping the model in the same package as the flow narrows that gap. It also has a price. The model is no longer a platform component; it’s part of one solution. The flow owner now carries the questions an IDP team used to carry: what is the acceptance criterion, which document sample was it tested on, and who is allowed to change it?

The score is only as good as the labels you confirmed

The documentation is explicit about measurement. The node’s health score is the average of the F1 scores of every field in the taxonomy. 80% and above is green, 40% to 79% is yellow, below 40% is red. The score comes from evaluation runs over all annotated documents in the node’s dataset. Document error rate shows how far predictions drift from user annotations, and it can exceed 100%. UiPath recommends annotating at least ten values per field, ideally across ten different documents, and using the same dataset when comparing versions.

It’s a sound framework, but I’d keep two things in mind. First, the score is computed against the labels you confirmed, so a wrongly confirmed value becomes the reference and pushes the score up. Second, averaging across fields assumes every field matters equally. An IBAN and a free-text description line do not. My rule is to write acceptance criteria per field, weighted by business impact: one threshold for payment and tax fields, another for the rest. A green health score is not, on its own, a production sign-off.

Five gaps the documentation leaves open

GapWhat the documentation saysWhat I’d do before production
No performance alertsIXP in Flow does not yet offer notifications or alerts on model performanceSchedule evaluation runs on a fixed dataset and track the correction rate in Validate extraction every week
Only the creator sees the traceNobody but the user who generated a prediction can view its traceWrite down where operations will investigate failures instead (the IXP models tab in Orchestrator, the Files tab)
Audit entries visible for 60 daysThe AI Trust Layer logs each extraction as one entry, visible for 60 days; pre- and post-processing are not auditedIf your retention policy is longer, put the export job in the deployment plan
Validation node only in the same flowValidate extraction does not work with an Extract node bound to a published model or another flow’s modelFor shared models, build human validation with Action Center or Validation Station
Token limits can fail quietlyOn documents with many fields, predictions may come back incomplete or empty, and runtime confidence values return 0Route every document with zero confidence or empty output straight to exceptions

The last row deserves a second look. The documentation says page and token limits vary by model family and version, and gives no figures. Its example is an 80-page document with 1,400 extracted values, which may trigger a token warning in the interface. In other words, the failure can be silent: the flow doesn’t break, the data just arrives incomplete. Without a rule-based check, a gap like that can travel all the way into a ledger entry.

When I would not build the model inside the flow

A model built inside the flow works best when one team handles one family of documents. Taxonomy and validation rules sit with the same person, and the version sits in the same package.

If the model will serve several solutions with different owners, I’d choose differently: build and publish it in the IXP application and bind it read-only in each flow. The cost is known. You lose the Validate extraction node and have to set up human validation separately. In exchange, a taxonomy change by one flow owner doesn’t quietly reach everyone else’s solution.

There are two more cases where I’d wait. The feature is in preview, so I wouldn’t move production invoices onto it yet. And the guide I read is the Automation Cloud documentation; where documents can’t leave the building and the platform runs on premise, availability has to be confirmed separately. The airline programme runs in the client’s own data centre, and in an environment like that this question comes before every other one.

Five questions for Monday

Before a team tries this, I’d ask them five things. Who owns this model, and who can change its taxonomy? Which fields have their own acceptance threshold, and which document sample was it measured on? When performance drops, who notices first? Where do the audit entries live after 60 days? And where in the line does a document with zero confidence stop?

If those answers are written down, bringing the model into the flow does simplify the work. If they aren’t, you’ve just gathered the same mess onto a single canvas.
