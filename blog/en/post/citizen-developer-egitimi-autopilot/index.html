If an agent writes the draft, what should citizen developer training teach?

Autopilot is in preview as a coding agent in Studio Web. Starting from a 10-week citizen developer course we began at a large holding, how I would build it today.

Use case·Leadership & teams·November 12, 2026·7 min read·Türkçesini okuyun

Most citizen developer courses are judged by one question: after ten weeks, can the participant build an automation alone? I think that question has aged. UiPath’s Autopilot now runs as a coding agent in Studio Web, and it can take a requirement written in plain language, plan it and build a draft. If the agent writes the draft, three skills are left for the course to measure: reading what was generated, knowing which work is not yours to automate, and handing work over to the centre properly.

What we delivered and what I recommend

In February 2026 BOTTEQ started a 10-week UiPath Citizen RPA Developer course at a large holding. Our Automation & AI Solutions team lead taught it. The goal was to grow the number of citizen developers inside the organisation. I am not sharing the client’s name, the number of participants or the internal detail of the programme.

The rest of this piece is not a record of that course. In February, Autopilot did not exist in Studio Web in its current form. The design below is what I would change if I built the same course today. The product facts come from UiPath’s own pages, listed at the end.

How a business-unit idea reaches a shared folder

What we delivered is this: in February 2026 we started a 10-week UiPath training course at a large holding to grow its number of Citizen RPA Developers. The flow below is not that course’s content. It is the path I would want such a programme to end in now that Autopilot is here, and all of it is my recommendation.

Human

Idea record

The business user writes the case on one page: how often the task runs, how long it takes, which systems it touches, which data it reads and writes.

Rule

Boundary check

A written rule list decides. Personal data, writing to financial records or work that affects more than one unit sends the case to the centre. Otherwise the user may build it.

Model

Plan and draft

Autopilot turns the plain-language requirement into a plan. In the project types it supports it builds the draft; in the others it explains and reviews the existing project.

Human

Read and explain

The citizen developer reads the draft step by step and describes each step in their own words. If one step is left that they cannot describe, the automation does not move on.

Rule

Analysis and policy

Workflow Analyzer rules and the allowed-package list run automatically. The Automation Ops policy keeps publishing outside the personal workspace switched off.

Human

Centre review

A developer from the centre of excellence checks error handling, logging and credential use, and writes down the decision with a reason.

System

Release and inventory

The automation goes to the shared folder and gets a line in the inventory: owner, measure, date of last review.

What changed

According to the Autopilot release notes, “Autopilot as a coding agent in Studio Web” was released in public preview on 23 September 2026; the note was added to the page two days later. UiPath describes it as the same coding agent that ships with Studio Desktop. Nothing needs installing.

The user guide lists eight project types: Maestro Flow, Maestro BPMN, Maestro Case, agents, API workflows, RPA workflows, coded apps and functions. The use cases include planning an automation from a process definition document or a plain-language requirement and then building it, running a project and finding the cause of a failure, and explaining an unfamiliar project step by step.

Support differs by project type, and that is the distinction that matters for a citizen developer. The Studio Web release notes say Autopilot builds API workflows from a description, then validates, runs and publishes them. For RPA workflows, coded apps and functions it currently reads, explains and reviews project files. So for the project type a business user builds most often, Autopilot in Studio Web is today mostly a reading and review assistant.

Three things are written down on the administration side. Administrators set the available models, the autonomy level, the enabled tools and the allowed MCP servers through Automation Ops. Every model request goes through the AI Trust Layer. Autopilot is included in the licence, with a monthly usage allowance per user; the page does not say how large that allowance is.

The Studio Web policy in Automation Ops also has two toggles that concern a course. One is “Allow Autopilot UI”, renamed in early October, which governs access to the Autopilot interface. The other lets users publish outside their personal workspace, and it is on by default.

How I would split the ten weeks today

Over my career I have designed UiPath and Blue Prism curricula from beginner to advanced for clients and internal teams. Their weight always sat on building: find the activity, drag it, connect it. Today I would move the weight to reading and deciding.

WeekSubjectWhat the participant can do
1–2Case selection and boundariesWrites up three cases from their own unit and argues which one belongs to the centre
3–5Building blocks, by handBuilds a small flow with variables, selectors, error handling and logging without the agent
6–7Working with AutopilotWrites the requirement, reads the plan, explains every generated step, finds and fixes a wrong one
8Broken dataRuns the flow with missing, wrong and unexpected data and records what happens
9HandoverClears the Workflow Analyzer output, fills in the review form, writes the inventory line
10Final casePublishes a real task and presents the time saved with the number they measured

I left weeks three to five without the agent on purpose. Someone who has never built error handling by hand will not notice that it is missing from a flow Autopilot produced. Building by hand has become a reading skill more than a production skill, and it still cannot be skipped.

The test for weeks six and seven is simple. Give the participant a flow that Autopilot generated and ask what each step does and what happens when it fails. UiPath’s release note says the same thing in one line: review generated changes before you run or publish them. A course should turn that sentence into a habit.

Handover: the least practised week

I have written before that the citizen developer approach creates fast, measurable value. I also wrote the condition in the same sentence: when it is combined with the right use-case selection and a sustainable architecture. Sustainability is decided in week nine, at handover.

With our clients we write governance rules such as code review standards, naming and logging conventions, release management and bot monitoring. A citizen developer programme needs a lighter version of those rules. I would fix three things technically:

  1. The publishing boundary. During and after the course, keep the toggle for publishing outside the personal workspace off for the citizen developer group. Reaching a shared folder goes through the centre’s review.
  2. Package and activity lists. The policy page lets you define allowed or prohibited lists of packages and activities. Open the activities that send email, delete files or write to a database for this group deliberately.
  3. Autopilot’s settings. Set the autonomy level and the allowed MCP servers for the group yourself. The logic I described for Autopilot in Orchestrator applies here too: every connected server is a new area of authority.

What it costs and where it is wrong

This design has three costs. The first is tying a curriculum to a feature in preview. Autopilot’s support in Studio Web differs by project type and will keep changing. On 6 November the sections and labels of the create menus were reorganised; training material built on screenshots ages quickly at this pace. Budget for rewriting weeks six and seven every term.

The second is the usage allowance. Because the page gives no figure, I do not know whether two weeks of heavy use by a class of fifteen would exceed it. Try it with a small group before the course.

The third is that centre review creates a bottleneck. If no developer time is set aside to review the output of forty citizen developers, the queue grows and people start working around the rule.

There are also cases where the programme is the wrong choice. If you have a handful of curious users, ten weeks is too much; seating them next to a developer in the centre is cheaper. If most of your processes touch customer data or financial records, the space left for citizen developers is narrow anyway. I covered the literacy side separately in the piece on role-based training.

One measure for Monday

The number of citizen developers is a fair starting target. I would put a second number next to it: the automations that, ninety days after the course, still run, have a named owner and have a line in the inventory. If you cannot state that number today, the first job before the next course is to build the inventory. A new curriculum can wait.
